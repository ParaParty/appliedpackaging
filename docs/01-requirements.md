# 需求文档

## 1. 项目目标

Applied Packaging / 应用封装是一个 AE2 附属 Mod。它给 AE2 自动化体系增加一层“包裹化物流”：

```text
AE2 样板语义 / 相邻存储内容
-> 包裹
-> 包裹路由、过滤、暂存、拆包
-> 目标机器 / 目标网络
```

这个 Mod 不做通用压缩库存，也不做普通箱子替代品。它只解决一个明确问题：把一批应该被一起移动、过滤、等待或拆入机器的资源封装成一个可路由的包裹单元，并且让这个单元仍然尊重 AE2 的样板、网络、总线和存储心智。

## 2. 目标用户

目标玩家已经熟悉 AE2 自动合成、Pattern Provider、Storage Bus、Export Bus、Interface 子网和存储元件。他们希望把复杂机器输入拆成有颜色和标记的物流包，并通过 AE2 网络或其他物流 Mod 进行路由。

## 3. 核心场景

彩色自动合成：

```text
主网 Pattern Provider
-> ME 包裹装配室
-> 红/蓝/Fluix 等多个包裹
-> 包裹子网或普通物流线
-> 包裹拆包总线 / ME 打包机
-> 目标机器
-> 产物回主网
```

Create 式 ME 子网打包：

```text
ME Interface 子网 / 相邻 AE 设备或线缆
-> ME 打包机
-> 包裹
-> 物流线
-> ME 打包机或包裹拆包总线拆入目标
```

包裹路由与暂存：

```text
AE 网络中已经存在红色包裹、蓝色包裹、带 marker 的包裹
-> 包裹存储总线只暴露包裹物品
-> 包裹卸货总线把匹配包裹完整拆入目标库存
-> 总线绝不把包裹内部内容伪装为散装库存
```

## 4. 功能性需求

R1. Mod 必须注册 17 个独立包裹物品：Fluix 默认色 + 16 个 Minecraft 染料色。颜色由 item id 决定，不仅写入 NBT；物品形态和丢出实体使用同一包裹模型渲染。

R2. 玩家不能正常获得“空包裹”。没有 `PackageData` 的包裹只能作为内部/调试状态存在，不进创造标签，不进正常配方链，不被物流系统接受。

R3. 包裹允许堆叠，但只有完全相同的包裹才能堆叠。一个 `红色包裹 x16` 表示 16 个相同包裹，而不是一个包裹装了 16 倍内容。

R4. 包裹内容必须以 AE2 泛型资源建模，核心结构是 `List<GenericStack>`，其中每项是 `AEKey + amount`。数据模型和端点适配不能写死成 `ItemStack`；只支持物品的相邻 Forge 端点必须保守拒绝其它 key。

R5. 包裹不允许真实嵌套。当打包输入中出现包裹时，必须展开后再封装，表现为合并、改色或追加内容。

R6. ME 包裹装配室必须支持三种正式样板语义：包裹样板按样板定义生成一个包裹；普通 AE2 处理样板把样板输入生成一个默认 Fluix、空 marker 的包裹；高级处理样板按输入列颜色一次生成多个有序包裹，marker 固定取处理样板主产物。包裹不允许自定义名称。所有模式仍受合成进度、AE 能量、加速卡、严格有序单包输出和阻挡规则约束。项目正式发布前不保留旧样板载体、旧 NBT schema 或开发版存档迁移。装配室不提供额外颜色或 marker fallback 配置；GUI 的槽位 hover、升级面板、空升级槽、已编码样板空槽图标和容量元件空槽图标必须使用回移的 AE2 当前 main 视觉。

R7. ME 打包机必须支持一个可切换连接面，并让机器背面始终作为第二个 AE 网络连接面；放置在地面时默认形成底部与背面两个可接线面，两者接入同一 AE2 主节点，其它面只暴露普通包裹输入/输出。机器支持手动/红石触发打包、包裹拆包、源包裹展开后再封装、基础 1k 容量与 16 类型上限，以及通过 AE2 16k / 64k / 256k storage component 切换对应容量档；同时支持颜色/marker 策略、打包内容过滤、拆包包裹过滤、反转卡内容过滤反转、GUI 工作进度展示和 GUI shift-click 单包输入。完成打包后的包裹必须停在去除 4px 后部模块后所得 12x16 前部区域中心，包裹底面位于传送带顶面 `y=2/16`；包裹与帘子的动态渲染只允许位于从工作口向内 15px 的体积，不得进入机器最后 1px 背板，传送带 UV 滚动停止后必须保留当前相位，下一次动画从该相位连续运行。打包机 GUI 的槽位 hover、升级面板、空升级槽和容量元件空槽图标必须使用回移的 AE2 当前 main 视觉；空 marker 槽使用 Applied Packaging 自有 marker 槽图标并提供说明 tooltip。

R8. 包裹样板必须在 AE2 原版 Pattern Encoding Terminal 中作为与 crafting / stonecutting / smithing 同级的包裹样板模式编码，并产出独立的 `appliedpackaging:package_pattern` 物品；不再提供独立 Package Pattern Terminal。原版终端的包裹模式使用高版本 AE2 124x66 模式面板，只显示清空、颜色按钮、3x3 可见输入窗口、左侧滚动条、marker 与自动输出；输入逻辑容量与 AE2 默认 processing pattern 相同，为 81 个 sparse 槽位，并支持数量显示、中键数量编辑、物品/流体容器和主产物 tooltip。该模式的空 marker 槽使用 Applied Packaging 自有 marker 槽图标、当前 main hover 和说明 tooltip。高级样板终端复用 AE2 原版终端主体，只保留处理样板编码，显示 4 个可见输入列和 4 行输出，按列配置包裹颜色并由主产物提供 marker，编码独立的 `advanced_processing_pattern`。包裹不提供任何自定义名称入口或名称元数据。所有拾色入口复用同一个纯颜色高层弹窗和同一个触发按钮实现；弹窗以参数决定是否显示 None，只有 Package Storage/Unpacking Bus 的过滤区允许 None，且其颜色按钮右键直接恢复 None。Fluix 与预留的 None 位置固定在最左侧分隔线内上下排列，None 隐藏时仍保留其布局空间，其余 16 色在右侧按 8x2 排列。选中态只替换 8x8 色格背景，不增加外边框或 hover 视觉；弹窗打开时必须拦截触发按钮自身及底层控件的 hover tooltip，不得重复 tooltip、隐藏底层物品或透传输入。

R9. 包裹存储总线与包裹卸货总线必须注册为 AE2 cable part，并只处理合法包裹；不再提供 Package Export Bus。两者共用最多 7 行包裹过滤规则，每行由可选模糊开关、可选反转开关、可为空的颜色选择、marker 过滤槽和 6 个普通物品过滤槽组成；颜色空模式表示不按颜色过滤，规则之间按“任一行匹配”处理。默认启用 2 行，每张容量卡额外启用 1 行，最多安装 5 张容量卡并在第 5 张时达到 7 行上限。第一、二行必须对应底图最上方两行，未启用行必须按新版 AE2 可选槽的透明叠加方式显示。模糊/反转按钮只在对应升级卡存在时显示，且无论只显示哪一种，都必须与颜色按钮保持相邻；模糊、反转、颜色三个 8px 按钮统一使用相对 18px 过滤行顶部 2px 的固定上边距，不做垂直居中。空 marker 过滤槽使用 Applied Packaging 自有 marker 槽图标；已解锁空槽 hover 时提供说明 tooltip，锁定行中的图标随槽背景使用相同透明度。包裹存储总线默认优先级为 0，沿用 AE2 当前 main Storage Bus 的 Help、清空、Partition Storage、存储配置工具栏、连接目标提示与升级面板视觉；Partition Storage 必须按相邻容器槽位顺序读取合法包裹，每个不同包裹生成一行颜色、marker 与可完整容纳的内容过滤，忽略散装物品和重复包裹，容器内没有包裹时清空过滤。包裹卸货总线采用 AE2 Formation Plane 式只写入网络端点，默认优先级同样为 0：只接收网络路由来的一个匹配包裹并输出其内容，不扫描或抽取已有 ME 存储，不枚举 held 包裹，也不提供网络抽取/一般存储功能。两个总线的默认值都为 0，玩家通过右上角 Priority 子菜单直接读写该数值，不存在隐藏偏移；数值不同时仍由较高者先接收，数值相同时必须由可接收该包裹的 Package Unpacking Bus 优先，只有拆包总线因 held 忙碌、过滤、阻挡或目标容量拒绝时才继续尝试 Package Storage Bus。其左侧按钮固定为 Help、清空过滤与 AE2 Pattern Provider 同类型的阻挡模式；阻挡开启时，若相邻目标已存在任一包裹内容物类型，则不接收或提交该包裹。卸货总线在同一 5 格升级库存中额外支持最多 4 张加速卡，并显示工作包裹槽和进度条；接收后本地持有包裹并运行与 ME 打包机拆包模式相同的 20 tick 进度，结束时对相邻 item handler 做整包累计模拟，全部可接收且满足阻挡要求后才逐项插入。最终检查拒绝时保留原包裹、显示阻塞并定时重新验证，工作中不可取出，阻塞/空闲时允许玩家取回，拆除 part 时必须返还。两者右上角均提供与 AE2 当前 main Storage Bus 一致的专用优先级标签入口；卸货总线的工作槽和进度条必须向左避让该入口。两者都不能把包裹内部内容伪装成散装库存，也不能把散装库存自动打成包裹。

R10. 所有整包操作必须先完成所需验证。MEStorage 打包在抽取、输出或容量模拟失败时不得提交；卸货总线在网络插入模拟和最终提交两个阶段都必须重新验证过滤、阻挡与完整目标容量，并采用与 AE2 Pattern Provider 相同的 check-then-push 约定：阻挡模式先检查目标是否已有任一输入类型，再在累计快照中模拟整包内容，全部可插入后才执行真实插入，不额外实现跨第三方 handler 的回滚事务。模拟失败不得写入目标，也不得接收或消耗本地持有包裹。

R11. Tooltip 必须明确显示“每包内容”和“堆叠总计”。高级信息使用 Shift/Ctrl 展示容量、类型数、hash、marker。

R12. 所有玩家可见内容必须有英文与简体中文语言文件。

R13. 必须提供可发布 jar、基础配方、loot table、模型、材质、logo/图标和 mods.toml 元数据；mods.toml 必须声明 Minecraft、Forge、AE2 与 GuideME 发布依赖范围。

R14. 玩家手持包裹并蹲下右键时可以手动拆开手中的整叠同款包裹；掉落实体包裹受到伤害时可以拆开并把内容掉落到世界中。手动拆包不得部分提交；无法转换为普通物品掉落的内容不得销毁包裹。

## 5. 非功能性需求

NF1. 目标平台先固定为 Minecraft 1.20.1 Forge。由于 1.20.1 没有 Data Component，包裹数据使用 ItemStack NBT 保存；业务代码必须通过 `PackageDataStorage` 抽象读写，为未来 1.20.5+ Data Component 适配留接口。

NF2. 公共逻辑必须和 Minecraft/Forge API 解耦到可单元测试的程度。包裹 canonical hash、容量计算、过滤、合并计划应能在普通 JVM 测试中验证。

NF3. 客户端渲染、菜单、屏幕、颜色处理必须和服务端逻辑分离，确保 dedicated server 不加载客户端类。

NF4. 行为敏感逻辑必须考虑 GameTest。至少覆盖包裹序列化、MEStorage 打包/拆包、item handler 整包累计模拟、过滤与容量拒绝。

NF5. 资源制作必须保留资产契约、来源和验证记录，避免临时图片无法复现。

NF6. 发布构建不得包含调试物品、临时测试资源、未使用模板包或本地绝对路径。

## 6. 范围边界

正式做：

```text
17 色独立包裹
无空包裹玩法
包裹堆叠
包裹套包裹时展开再封装
GenericStack 数据模型
ME 包裹装配室
ME 打包机
ME Interface 子网相邻识别
ME 打包机基础 1k 容量与 16 类型上限
ME 打包机 16k / 64k / 256k 容量元件升级
装配室 16k / 64k / 256k 容量元件
包裹样板
高级样板终端
独立高级处理样板物品与包裹列 NBT 元数据
包裹存储总线
包裹卸货总线
统一过滤系统
基础材质、模型、配方、语言文件、GameTest
```

暂时不做：

```text
4k 容量档
MEGA Cells 等附属大容量兼容
复杂动画
多输出口装配室
批量编辑终端
多包裹路线可视化
Fabric/NeoForge 现代版多加载器
```

明确砍掉：

```text
空包裹
真实包裹嵌套
包裹本身有有序/无序模式
ME 打包机读取 Pattern Provider / pushPattern
ME 打包机理解普通/彩色/包裹/封装处理样板
ME 包裹装配室执行相邻存储打包
ME 包裹装配室拆包
包裹存储总线把包裹内容伪装成散装库存
Package Export Bus
独立 Package Pattern Terminal
any / all / exact 过滤模式
装配室阻挡模式扫描整个输出网络
打包机直接扫描自己所在的任意 AE 网络
```
